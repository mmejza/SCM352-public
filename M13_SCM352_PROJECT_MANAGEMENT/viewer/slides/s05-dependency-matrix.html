The Dependency Matrix
First tool — makes implicit activity relationships explicit
Structure — Three Columns
ColumnContains
Activity LetterSingle capital letter (A, B, C …) assigned in rough execution order
DescriptionBrief label for the work package (e.g., "Procure equipment")
Predecessor(s)Letters of activities that must be fully complete before this activity can begin. Dash (—) if none.
Two Rules for Building the Matrix

Rule 1: Every distinct work package gets its own row — even if two activities happen simultaneously.

Rule 2: For each activity, ask: "What must be 100% finished before this can start?" List only true technical requirements — not scheduling habits or resource conflicts.

Why the Predecessor Column Is the Hard Part

Activity lists are easy. Predecessor classification is where projects go wrong.

Three categories to distinguish:

True dependency: Logic or physics — software cannot be tested before it is written.

Resource constraint: The same team does both activities, so they are sequenced. With a second team, they could run in parallel. This is NOT a true dependency.

Organizational habit: "We always do review before design." But if preliminary specs would satisfy the review, the dependency is a preference, not a requirement.
