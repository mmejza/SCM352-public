True Dependency vs. Scheduling Preference
The predecessor classification question — the most consequential judgment in building a dependency matrix
True Technical Dependency

Test: Could this activity start before its predecessor is complete, even with unlimited resources and staff? If NO — it is a true dependency.

Examples:

  • Software cannot be tested before it is written.
  • Equipment cannot be installed in a building that does not yet exist.
  • Staff cannot be credentialed with an insurer before they are hired.

These belong in the predecessor column. They cannot be relaxed without rework risk.

Scheduling Preference (Not a True Dependency)

Test: Could this activity run in parallel if we had a second team or unlimited capacity? If YES — this is a resource constraint or habit, not a dependency.

Examples:

  • Documentation written after development — only because the same person does both.
  • Regulatory review held until after design — but preliminary specs would satisfy the review.
  • "We always do A before B" — true historically, but not technically required.

These do NOT belong in the predecessor column. Adding them extends the critical path unnecessarily.

Why This Matters for the Critical Path

Every false dependency in the matrix adds duration to some path. If the false dependency happens to be on the critical path, it extends the project deadline — not because the work requires it, but because the plan assumes it. Projects add weeks to their schedule before the first task begins when predecessor classification is done carelessly.
